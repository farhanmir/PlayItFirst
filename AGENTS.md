# Play It First — instructions for coding agents

## Workflow
- Owner requests local Codex work directly on `main`, with small focused commits and pushes. Do not create new branches or PRs for routine tasks. Fetch and inspect remote main before editing; never force-push, reset, discard uncommitted work, or overwrite teammates' changes. Coordinate with the owner before concurrent edits to shared files. Run targeted tests and typecheck before pushing; run build for UI/deployment changes.
- Local Codex is the primary coding agent; do not use Cursor Cloud (usage exhausted). Cloud agents that inherently require isolated branches/PRs are not the default. Do not launch them unless owner explicitly requests that workflow. Existing QA PR #5 is evidence to review, not automatic authorization to merge; incorporate useful tests in coordination with local work.
- Read issue #2 and latest docs/PROGRESS.md. Preserve working architecture and integrations; update progress with actual evidence, screenshots when available, and blockers. No new stretch features until the core game is enjoyable.

## Product priority: GAME FIRST, not dashboard
Play It First is a playable business, not a dashboard with a 3D preview. The owner's current playtest finds it dashboard-like. Make an immediately enjoyable playable café before adding more features. Keep the shared authoritative Node/WebSocket simulation and existing R3F renderer. One polished café and one complete human-played shift are better than many panels. Reference art direction: cozy first-person café simulator, Sims-style build mode, Overcooked-like service and feedback. These are inspiration, not assets; use original procedural meshes or appropriately licensed assets with attribution, no ripped game assets.

### P0: player-facing experience
1. Make the 3D scene the dominant full-viewport experience on desktop and phone. Default to directly playable view with minimal game HUD. Hide finance/integration/analytics/crew/log panels behind an optional pause/management drawer. Keep QR invite and sound/controls accessible. Don't let phase, previous camera selection or a fallback hide the playable scene. Verify actual WebGL rendering (including errors, dimensions, camera, lighting), not just compile.
2. A single guided playable shift: spawn at a useful position, show customers entering, queueing, readable order bubbles, take order at counter, walk to espresso machine, visible brewing progress/steam, carry visible cup, deliver to pickup/customer, satisfying payment/audio and next order. No demo automation performing the player's job before they can interact. Retain keyboard and mobile touch controls; clear context action near station, optional click interaction; no hidden keyboard-only dependency. Show authentic orders, inventory and cash changes only after server accepts action.
3. Improve actual world aesthetics: warm sunlight through windows, readable materials and lighting, cohesive cozy palette, polished floor/walls, recognizable countertop/espresso equipment, cups, shelves, plants, menu sign, stylized customers with readable silhouettes and walk/idle animations. Focus on art composition and performant assets, not piling on polygons or expensive effects. Make camera/controls smooth and preserve phone performance. No static image pretending to be gameplay.
4. Build mode: one obvious toggle/hotkey, Sims-like furniture catalog overlay, ghost preview with valid/invalid placement, drag/rotate/snap and real collision constraints; existing tabletop can remain secondary. Moving a station while others play updates all clients and actual NPC routes. Don't pause global play just to let an owner edit; implement per-client editor state if necessary.
5. Keep only compact cash/served/active order HUD during service. Show finance, timeline, blueprint and sponsor context outside the moment-to-moment game. Preserve existing features behind optional interfaces, don't delete functional integrations.
6. Fix QA #5 bugs in the actual simulation (invalid serve/auto-sales bypass stock, repeat collect, negative balance, walking through equipment). Use real order lifecycle and shared validated actions. Preserve tests; no invented metrics.
7. Verify both desktop and phone visually. Capture real screenshots or a short clip of the playable café, build mode, order interaction and two-player join; report actual browser/device tested. Don't claim the scene matches reference images unless verified.

## Deployment: Render only (free full-stack)
- Production URL: https://playitfirst.onrender.com/. Use the existing Render Web Service and render.yaml on main; Vercel and other split-hosting deployments are discontinued. Do not recreate Vercel configuration, projects or separate frontend hosting.
- One persistent Node process serves the built Vite SPA, /api/* and /ws. Frontend uses same-origin HTTP and WebSocket URLs. Keep local single-port development intact and preserve proxy-aware HTTPS QR invites and resume tokens. Do not set legacy split-host frontend environment overrides.
- Keep sponsor secrets in Render's Environment/Secret Files or an ignored local .env. Never commit keys or restricted sponsor files. Coordinate deployment with Hrudai (issue #6); run the existing deployment smoke check and report actual deployed commit and browser/phone results, not inferred success.
