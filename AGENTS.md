# SoftOpen — instructions for coding agents

## Workflow
- Owner requests local Cursor work directly on `main`, with small focused commits and pushes. Do not create new branches or PRs for routine tasks. Fetch and inspect remote main before editing; never force-push, reset, discard uncommitted work, or overwrite teammates' changes. Coordinate with the owner before concurrent edits to shared files. Run targeted tests and typecheck before pushing; run build for UI/deployment changes.
- Cloud agents that inherently require isolated branches/PRs are not the default. Do not launch them unless owner explicitly requests that workflow. Existing QA PR #5 is evidence to review, not automatic authorization to merge; incorporate useful tests in coordination with local work.
- Read issue #2 and latest docs/PROGRESS.md. Preserve working architecture and integrations; update progress with actual evidence, screenshots when available, and blockers. No new stretch features until the core game is enjoyable.

## Product priority: GAME FIRST, not dashboard
SoftOpen is a playable business, not a dashboard with a 3D preview. The owner's current playtest finds it dashboard-like. Make an immediately enjoyable playable café before adding more features. Keep the shared authoritative Node/WebSocket simulation and existing R3F renderer. One polished café and one complete human-played shift are better than many panels. Reference art direction: cozy first-person café simulator, Sims-style build mode, Overcooked-like service and feedback. These are inspiration, not assets; use original procedural meshes or appropriately licensed assets with attribution, no ripped game assets.

### P0: player-facing experience
1. Make the 3D scene the dominant full-viewport experience on desktop and phone. Default to directly playable view with minimal game HUD. Hide finance/integration/analytics/crew/log panels behind an optional pause/management drawer. Keep QR invite and sound/controls accessible. Don't let phase, previous camera selection or a fallback hide the playable scene. Verify actual WebGL rendering (including errors, dimensions, camera, lighting), not just compile.

No demo automation performing the player's job before they can interact. Retain keyboard and mobile touch controls; clear context action near station, optional click interaction; no hidden keyboard-only dependency. ## Deployment: Vercel front end + persistent backend
User wants a public playable URL. Keep local single-port dev intact. Vercel can deploy the Vite static frontend, but current server holds authoritative rooms/timers in memory; use a persistent Node service (Railway or equivalent) for game API/WebSocket, not independent function instances. Vercel now has WebSocket beta, but function duration and state across instances make direct lift-and-shift unsafe for this implementation.
- Add optional public API and WebSocket origin config (e.g. VITE_API_BASE_URL and VITE_WS_URL) with same-origin defaults locally. Audit all fetch calls, socket reconnect and invite QR generation; QR must point to public frontend HTTPS URL, socket to actual backend WSS, including behind proxies. Use explicit frontend/public origin and controlled CORS; no credentials in VITE_* variables. Add config docs and test the two-client flow across the deployed origins. Backend remains authoritative and one instance for hackathon demo.
- Add suitable Vercel Vite build/output config and persistent backend production start/build configuration as needed. Do not claim deployment succeeded without a public URL and actual testing. Owner must authorize hosting accounts and provide secrets through their dashboards. Do not commit secrets. Fix .env loading in local server if needed.
